# Заргота — возможные апгрейды ведения сессии

Статус: проектный TODO, решения требуют поэтапного согласования.

Дата ревизии: 13.08.2026.

Область: визуал сессии, пульт ГМ, кубики, редактор сцены,
атмосфера, инструменты ведущего, производительность и надёжность.

Этот документ собирает обсуждённые идеи в одном месте и сортирует их по типу
работ. Он **не заменяет** существующие планы:

- [`SESSION_PRODUCT_SCOPE.md`](SESSION_PRODUCT_SCOPE.md) — продуктовые границы;
- [`SESSION_REFACTOR_TODO.md`](SESSION_REFACTOR_TODO.md) — данные, комнаты,
  reconnect и основной рефакторинг;
- [`GM_GAMEPLAY_SYSTEM_TODO.md`](GM_GAMEPLAY_SYSTEM_TODO.md) — уже реализованная
  выдача, статусы, предметы и базовый каст;
- [`SPELLS_TODO.md`](SPELLS_TODO.md) — отдельный канонический план коллекции,
  изучения, подготовки, улучшения и боевого применения заклинаний;
- [`COMBAT_VFX_FOUNDATION_PLAN.md`](COMBAT_VFX_FOUNDATION_PLAN.md) — общий
  runtime боевых эффектов;
- [`VTT_ROADMAP.md`](VTT_ROADMAP.md) — краткая дорожная карта VTT.

Задачи ниже нельзя считать обещанием одной большой переработки. Каждый крупный
блок сначала получает отдельный аудит текущего кода, небольшой проектный
контракт и проверяемый первый этап.

---

## 1. Как читать этот TODO

### Приоритет

- **P0 — обязательно для надёжной сессии.** Потеря данных, дубли, рассинхрон,
  невозможность провести ключевое действие.
- **P1 — необходимо для удобного ведения.** Сильно влияет на темп и ясность
  работы ГМ или игроков.
- **P2 — важный visual/UX upgrade.** Делает сессию красивее и быстрее, но не
  блокирует базовый сценарий.
- **P3 — эксперимент.** Выполняется только после прототипа и замеров.

### Сложность

- **S** — локальный интерфейс без нового сетевого контракта.
- **M** — несколько связанных UI/runtime-компонентов.
- **L** — общая модель данных или несколько клиентов.
- **XL** — новый тяжёлый renderer либо глубокая миграция; обязательно дробить.

### Статус задач

- `[ ]` — не начато;
- `[~]` — частично существует, нужен аудит и доведение;
- `[x]` — подтверждено текущими планами как реализованное; в этот документ
  заносится только как зависимость, а не как новая работа.

## 2. Неподвижные правила будущих апгрейдов

- [ ] Не создавать «Session v2» и не переписывать Firebase целиком.
- [ ] Сохранять продуктовую рамку: один ГМ и до пяти доверенных друзей; защищать
  прежде всего от потери данных, старых вкладок, reconnect и клиентских ошибок.
- [ ] Переиспользовать существующие заявки, outbox, `operationId`, reconnect,
  боевой runtime, каталог статусов, VFX и библиотеки ассетов.
- [ ] Разделять сетевое воспроизведение и presentation: сеть определяет **когда
  и ровно один раз**, renderer — **как это выглядит**.
- [ ] Не применять урон, статус, расход заклинания или другую необратимую
  механику до подтверждения ГМ, если действие требует решения мастера.
- [ ] Preview эффекта использует тот же runtime и preset, что и живая сессия.
- [ ] Визуальная деградация качества не должна менять правила, результат броска,
  состояние боя или Firebase-события.
- [ ] Не хранить большие изображения и повторяющиеся base64-копии в снимке
  комнаты; использовать путь/manifest/thumbnail.
- [ ] Для инструментов ГМ предпочитать понятные иконки, карточки, переключатели
  и прямое управление вместо длинных таблиц и «Excel-форм».
- [ ] Любой сетевой блок завершать сценарием «ГМ + игрок в разных клиентах»;
  автоматические проверки и ручная проверка пользователем отмечаются отдельно.

# КАТЕГОРИЯ A. Необходимое для ведения сессии

Это функциональность, которая непосредственно влияет на темп игры. Она выше
косметики, даже если некоторые визуальные задачи проще реализовать.

## A1. Единый пульт ведения ГМ — P1 / L

### Цель

Собрать разрозненные инструменты в одном рабочем пространстве, не дублируя
существующую логику вкладок, запросов, выдач и времени.

### Целевая структура

- [ ] Сохранить два независимых режима: **Ведение** и **Редактор**.
- [ ] В режиме «Ведение» сделать пять основных вкладок:
  - **Контекст** — выбранный герой, существо, зона или объект;
  - **Сцена** — время, атмосфера, показ, камера и раскрытие;
  - **Материалы** — предметы, карточки, письма, иллюстрации;
  - **План** — эпизоды, реплики, секреты, напоминания;
  - **Инструменты** — имена, таймеры, таблицы и диагностика.
- [ ] Показывать контекст выбранного объекта без открытия параллельного тяжёлого
  окна: HP, статус, видимость, принадлежность, быстрые действия.
- [ ] Оставлять не более шести закреплённых быстрых действий.
- [ ] Убирать из постоянного toolbar те действия, которые доступны в пульте или
  командной палитре.
- [ ] Сохранять размер, позицию, активную вкладку и свёрнутое состояние локально.
- [ ] При смене вкладок не пересоздавать весь пульт и не допускать мерцания:
  патчить только содержимое активной секции.
- [ ] Не закрывать незавершённую форму кликом по карте без предупреждения.

### Критерий готовности

ГМ проводит сцену, не переключаясь между несколькими перекрывающими карту
панелями; существующие Firebase-операции продолжают работать без нового канала.

## A2. Командная палитра ГМ — P1 / M

- [ ] Открывать через `Ctrl/Cmd + K` и отдельную компактную кнопку.
- [ ] Добавить поиск по действиям и сущностям, управление с клавиатуры.
- [ ] Первые команды:
  - призвать существо;
  - поставить или выдать предмет;
  - назначить/снять статус;
  - нанести урон или лечение с показом/скрыто;
  - изменить атмосферу;
  - показать карточку или иллюстрацию;
  - изменить время;
  - перейти к сцене/зоне.
- [ ] Недоступные команды объясняют причину, а не исчезают бесследно.
- [ ] Последние команды и избранное хранятся локально, без Firebase-записи.

## A3. Рабочий план и подсказки ведущего — P1 / M

- [ ] Создать компактную «ленту эпизода»:
  - что описать;
  - что сказать;
  - кого представить;
  - какой секрет держать;
  - какую проверку запросить;
  - какой материал показать.
- [ ] Поддержать галочки, drag-порядок и кнопку «следующий пункт».
- [ ] Связать пункт плана с зоной, NPC, карточкой, заметкой или эффектом, но не
  запускать их автоматически без явного действия ГМ.
- [ ] Добавить режим «только текущий пункт», чтобы план не занимал экран.
- [ ] Хранить черновик плана безопасно и не терять введённый текст при закрытии.

## A4. Быстрый призыв существ — P1 / L

- [ ] Искать по существующему Бестиарию, а не создавать второй каталог.
- [ ] Показывать компактные фильтры: тип, роль, сложность, фракция, избранное,
  недавно использованные.
- [ ] Перед призывом задавать:
  - количество;
  - отношение к группе;
  - видимость;
  - включение в раунд;
  - стартовые HP/статус;
  - точку или область появления;
  - длительность для временного призыва.
- [ ] Публиковать боевой snapshot существа, сохраняя источник в Бестиарии.
- [ ] Не хранить полную копию тяжёлых медиа в комнате.
- [ ] Не допускать повторного призыва одной заявки после reconnect.

## A5. Заклинания в сессии — P1 / L

Подробная модель заклинаний больше не ведётся в этом общем документе. Коллекция
героя, состояния «найдено / изучено / подготовлено», базовые девять слотов,
врождённые способности, выдача из Каталога, заявки на изучение, боевая палитра,
улучшения и Firebase-доставка описаны в [`SPELLS_TODO.md`](SPELLS_TODO.md).

- [ ] При реализации следовать очереди и контрактам `SPELLS_TODO.md`.
- [ ] Здесь учитывать только межсистемные зависимости: статусы, Бестиарий,
  броски, VFX, exactly-once playback и reconnect.

## A6. Атмосфера сцены — P1 / L

- [ ] Разделить два разных понятия:
  - **постоянная атмосфера:** дождь, туман, снег, пепел, пыль, ветер;
  - **одноразовый cue:** вспышка, толчок, гром, священный импульс.
- [ ] Для атмосферы хранить компактное состояние сцены:
  интенсивность, направление, скорость, цвет, звук, quality profile.
- [ ] Для cue использовать существующий exactly-once `visualEvent`.
- [ ] Рендерить постоянную погоду общим canvas/runtime, а не таймером на каждую
  частицу и не повторяющимися Firebase-событиями.
- [ ] Добавить локальный preview перед публикацией игрокам.
- [ ] Плавно переходить между состояниями без резкой полной перерисовки.
- [ ] Останавливать/упрощать эффект в скрытой вкладке и low-quality режиме.

## A7. Выдача, письма, места и материалы — P1 / M

- [~] Переиспользовать существующие типы item/quest/text/image и историю выдач.
- [ ] В интерфейсе явно разделить:
  - один предмет;
  - набор предметов;
  - письмо/текст в журнал;
  - цель/задание;
  - место;
  - иллюстрацию/сцену.
- [ ] Для каждого типа показывать только относящиеся к нему поля и preview.
- [ ] Объяснить пользователю названия «Библиотека», «Подготовленные карточки» и
  «История», избегая непонятного термина «Картотека» без подсказки.
- [ ] Письмо сохранять в журнале как отдельную читабельную карточку; изображение
  показывать как обложку/газетную иллюстрацию над текстом.
- [ ] Место сохранять в отдельной категории журнала и разрешать связать с зоной.
- [ ] Поддержать выбор нескольких получателей с понятными галочками.

# КАТЕГОРИЯ B. Визуальные и UX-апгрейды

Эти задачи должны менять представление, но по возможности не затрагивать
Firebase-схему или правила боя.

## B1. Новый визуальный язык кубиков — P2 / L

- [ ] Сохранить тёмный камень, металл и золото как базовый стиль.
- [ ] Перейти от отдельной «наклейки-числа» к подготовленным числам на гранях или
  устойчивой face-mask, которая движется вместе с кубиком.
- [ ] Для первого прототипа использовать **2.5D**:
  - готовая геометрия;
  - несколько дискретных landing-положений;
  - face texture/mask;
  - управляемая тень и подсветка.
- [ ] Не переходить сразу на Three.js/полную физику без сравнительного прототипа
  по FPS, размеру ассетов и одинаковости результата на клиентах.
- [ ] Сохранить читаемость d4, d6, d8, d10, d12 и d20 при уменьшении.
- [ ] Критические цвета, градация большого урона и надписи результата остаются
  отдельным presentation-слоем, а не частью текстуры кубика.

## B2. Размер и композиция броска — P1 / M

- [ ] Привязывать размер к сетке сцены, а не к абсолютному размеру экрана:
  ориентир d20 — около 1.5 клетки, d4–d12 — около 1.25 клетки.
- [ ] Для нескольких кубиков постепенно уменьшать размер и увеличивать область
  рассеивания, не перекрывая всю сцену.
- [ ] Ограничивать композицию viewport и рабочей областью карты.
- [ ] Итог привязывать к нормализованной зоне падения кубиков и показывать выше
  портретов/жетонов сцены, но не отвязывать от карты в полноэкранный слой.
- [ ] На всех клиентах использовать одну scene/world anchor, а не экранные
  координаты отправителя.
- [ ] Для 8–12 кубиков предусмотреть компактную кластеризацию и читаемый подсчёт.

## B3. Скины кубиков — P3 / L

- [ ] Определить presentation-only `DiceSkinSpec`:
  геометрия, материал, рамка, face mask, glow, звук.
- [ ] Скин не влияет на RNG, формулу, точный результат или права игрока.
- [ ] Первые варианты: обсидиан/золото, кость/железо, дерево/латунь,
  серебро/лазурь.
- [ ] Загружать только выбранный скин и thumbnail библиотеки.
- [ ] Перед общей реализацией проверить вес ассетов и время decode на слабом
  устройстве.

## B4. Плавность окон и слоёв — P1 / M

- [ ] Все toolbar popup открывать из окончательной позиции без первого кадра
  справа и последующего скачка.
- [ ] Использовать transform/opacity и один общий lifecycle открытия/закрытия.
- [ ] Не пересоздавать большие DOM-деревья при смене вкладки.
- [ ] Добавить единые состояния: loading, empty, error, disabled, saved, dirty.
- [ ] Сохранить `prefers-reduced-motion` и режим уменьшенных эффектов.

## B5. Сцена и токены — P2 / M

- [ ] Собственный герой игрока остаётся доступным над пересекающимися токенами,
  но без бесконтрольного глобального `z-index`.
- [ ] Статусы возле жетона кликабельны и открывают read-only объяснение игроку.
- [ ] Состояния «обычный / сражён / труп / скрыт» имеют разные компактные знаки,
  не закрывающие портрет и имя.
- [ ] Урон/лечение поддерживают мастерский переключатель публичного или скрытого
  показа анимации и числа.
- [ ] Иконки предметов, атак, статусов и действий берутся из единого
  оптимизированного media catalog, без emoji-fallback там, где есть ассет.

## B6. Редизайн карточек результата — P2 / M

- [ ] Обычная проверка: результат, модификатор, DC/AC и краткий исход.
- [ ] Критический успех/провал: более длинная, но не блокирующая презентация.
- [ ] Урон: последовательный подсчёт, визуальная градация и финальный impact.
- [ ] Преимущество/помеха: оба кубика остаются цельными, отклонённый результат
  визуально гаснет, выбранный переходит к итогу вместе с текстурой.
- [ ] Результат заявки появляется до анимации попадания по цели.
- [ ] Все звуки синхронизированы с фазами animation timeline, без второго
  конкурирующего impact-пика.

# КАТЕГОРИЯ C. Сложные технические и механические апгрейды

Эти задачи нельзя начинать только с CSS. Им нужен контракт данных, тесты и
отдельный безопасный аудит.

## C1. Единый контракт броска `RollIntent` — P1 / XL

Сейчас свободный бросок, заявка, бой и заклинание являются разными UX-входами.
Их не нужно превращать в одну кнопку, но результат должен проходить через один
нормализованный контракт.

- [ ] Определить поля:
  - `source`: free/request/combat/spell/GM;
  - `semantic`: check/attack/save/damage/healing/table/neutral;
  - массив кубиков и модификаторы;
  - публичность и получатели;
  - `sceneAnchor` в координатах мира;
  - автор/говорящий;
  - skin ID;
  - animation/sound profile;
  - стабильный event/operation ID.
- [ ] Сохранить отдельные входы UX, но использовать один renderer и result model.
- [ ] Для свободных non-d20 бросков добавить явный preset:
  **Урон / Лечение / Нейтральный / Таблица**.
- [ ] Запретить автоматически считать любой набор d4–d12 уроном.
- [ ] Не позволять смешивать d20 с damage dice там, где правила этого не
  предусматривают.
- [ ] Синхронизировать anchor так, чтобы каждый клиент видел бросок в одном месте
  своей сцены независимо от разрешения и камеры.
- [ ] Exactly-once claim распространять на кубики, итог и звук как на разные
  presentation-фазы одного события, а не разные логические броски.

## C2. Преимущество, помеха и сложные d20 — P1 / L

- [ ] Формально закрепить порядок показа двух результатов и паузу между ними.
- [ ] Для интриги сначала показывать больший, затем меньший результат; выбранный
  системой исход становится финальным только после второй фазы.
- [ ] При преимуществе учитывать больший, при помехе — меньший.
- [ ] Отклонённый кубик разрушается/гаснет целиком вместе с числом.
- [ ] Выбранный кубик и число перемещаются одной трансформацией.
- [ ] Критический текст выводить в финальном результате вместе с суммой, а не
  оставлять только возле кубика.
- [ ] Один d20 нельзя размножать обычным левым кликом в free-roll picker;
  преимущество/помеха включаются отдельным режимом.

## C3. Каноническая модель статусов — P0 / XL

- [~] Зафиксировать единый normalizer/build-функцию для листа героя, VTT, Arena,
  заклинаний и Firebase.
- [ ] Устранить расхождение между `statuses`, `tempEffects`, `statusEffects` и
  `conditions.effects` через совместимый адаптер, а не удаление legacy-данных.
- [ ] Хранить полный snapshot для undo: ключ, источник, длительность, стаки,
  иконка, цвет, tick, visibility.
- [ ] Панель ГМ, токен и лист героя читают один нормализованный источник.
- [ ] Добавить диагностический экран расхождения с безопасной кнопкой ремонта,
  доступной только ГМ.
- [ ] Не менять Firebase-схему без миграционного плана и round-trip тестов.

## C4. Жизненный цикл сущности — P0/P1 / L

# КАТЕГОРИЯ E. Оптимизация и визуальная диагностика нагрузки

Оптимизация начинается с измерений. «Стало плавнее на глаз» не является
достаточным критерием.

## E1. Компактный индикатор производительности — P1 / M

- [ ] В режиме ГМ показывать маленький chip, например:
  `58 FPS · VFX 3 · сеть OK`.
- [ ] Цвета: зелёный, жёлтый, красный; без постоянного большого debug-окна.
- [ ] Hover/click раскрывает:
  - средний FPS;
  - 1% low;
  - p95 времени кадра;
  - long frames;
  - активные VFX/particles;
  - число токенов/слоёв;
  - подписки и качество сети;
  - выбранный quality mode.
- [ ] Приблизительные пороги для 60 Hz:
  - зелёный: average ≥ 50 и 1% low ≥ 35;
  - жёлтый: average 35–49 или повторяющиеся кадры > 20 ms;
  - красный: average < 35 или устойчивые кадры > 34 ms.
- [ ] Помечать вероятную причину: DOM, canvas, images, VFX, dice, subscriptions,
  network; не выдавать эвристику за доказанный диагноз.

## E2. Один sampler и бюджет кадра — P1 / L

- [ ] Один централизованный `requestAnimationFrame` sampler вместо таймера на
  каждый виджет.
- [ ] Кольцевой локальный буфер последних 20–30 секунд без записи в Firebase.
- [ ] Не собирать тяжёлые stack trace в обычном режиме.
- [ ] Бюджетировать VFX отдельно от input/network/render UI.

## E3. Локальный нагрузочный тест — P1 / M

- [ ] Отдельная тестовая сцена без Firebase-записей.
- [ ] Presets:
  - 10 / 25 / 50 токенов;
  - 0 / 6 / 15 одновременных VFX;
  - fog/weather on/off;
  - несколько статусных знаков;
  - batch бросок кубиков.
- [ ] Тест длится около 20 секунд и возвращает короткий отчёт.
- [ ] Отчёт сравнивает high/balanced/low на одном устройстве.
- [ ] Не использовать тест как автоматическую гарантию качества реальной
  Firebase-сессии.

## E4. Автоматическое снижение только визуального качества — P2 / L

- [ ] Профили **High / Balanced / Low**.
- [ ] Ограничивать количество particles, projectiles, trails и одновременных
  погодных элементов.
- [ ] Снижать canvas DPR и частоту второстепенных декоративных кадров.
- [ ] Пауза/снижение в hidden tab.
- [ ] Не менять скорость логического таймлайна, RNG, исход боя и сеть.
- [ ] Возвращать качество вверх постепенно, без постоянного переключения.

## E5. Точечные оптимизации UI/runtime — P1/P2 / L

- [ ] Keyed patching токенов и строк вместо полного `innerHTML` большого окна.
- [ ] Локальный preview slider/drag; сохранение только на commit/debounce.
- [ ] Общий RAF и invalidation для движения, targeting и canvas effects.
- [ ] Object pools для частиц и transient DOM/VFX.
- [ ] `IntersectionObserver`/виртуализация для длинных библиотек.
- [ ] Thumbnail-first и lazy decode изображений.
- [ ] Явные `destroy/unsubscribe` при закрытии комнаты и больших окон.
- [ ] Render signature для вкладок, чтобы одинаковый snapshot не вызывал
  мерцание и повторное создание DOM.

# 3. Матрица зависимостей

| Блок | Требует сначала | Почему |
|---|---|---|
| Единый пульт ГМ | аудит существующих вкладок и render lifecycle | нельзя создать второй параллельный пульт |
| Заклинания | [`SPELLS_TODO.md`](SPELLS_TODO.md), канонический status adapter, текущий cast pipeline | эффект должен одинаково попасть в бой, токен и лист |
| Атмосфера | sampler/quality profiles, scene state | постоянный эффект не должен перегрузить клиентов |
| Новый renderer кубиков | `RollIntent`, world anchor, baseline FPS | иначе новый визуал закрепит текущие дубли и координатные ошибки |
| Скины кубиков | единый renderer и asset manifest | скины не должны размножать логику и тяжёлые файлы |
| Новый редактор сцены | draft/publish contract, asset manifest | нужен безопасный undo и контроль публикации |
| Интерактивные triggers | зоны/объекты со стабильными ID | нельзя привязывать автоматику к временным DOM-элементам |
| Автокачество | достоверный sampler и нагрузочный тест | деградацию нельзя настраивать вслепую |

# 5. Сценарии обязательной проверки

## Без сети

- [ ] Открытие/закрытие и изменение размера пульта.
- [ ] Смена вкладок без мерцания и потери черновика.
- [ ] Редактор сцены: drag, undo/redo, локальное сохранение и публикация.
- [ ] Нагрузочный тест в high/balanced/low.
- [ ] Новый renderer кубиков: каждый тип, 1/2/4/8/12 кубиков.

## ГМ + один игрок

- [ ] Разные разрешения и камеры показывают бросок в одной world-зоне.
- [ ] Обычный бросок, урон, лечение, d20, преимущество и помеха не дублируются.
- [ ] Каст: цель → проверка → эффект → списание после подтверждения.
- [ ] Призыв создаёт сущность один раз и переживает reconnect.
- [ ] Атмосфера плавно включается, меняется и выключается у обоих клиентов.
- [ ] Выдача/письмо/место появляется у правильного героя ровно один раз.

## ГМ + несколько игроков

- [ ] Индивидуальные материалы не видны другим участникам.
- [ ] Групповая выдача приходит каждому выбранному герою один раз.
- [ ] Броски разных участников не используют один presentation ID.
- [ ] 25+ токенов и несколько VFX не блокируют ввод и сетевые подтверждения.

## Reconnect и старая вкладка

- [ ] Повторный snapshot не повторяет roll, звук, impact, cast или delivery.
- [ ] Просроченная inactive-вкладка не становится вторым отправителем.
- [ ] Черновик ГМ не теряется, но не публикуется игрокам без подтверждения.
