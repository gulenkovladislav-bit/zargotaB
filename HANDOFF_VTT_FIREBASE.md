# Zargota VTT — хэндофф по сетевому режиму (для Codex)

Документ-контекст для передачи задачи другому агенту (Codex). Приветствуется альтернативное
мнение по архитектуре — если увидишь путь лучше предложенного, предлагай.

---

## 1. Что за проект

- Настольная D&D-компаньон-игра «Заргота». Всё живёт в **одном статическом файле `index.html`**
  (~2.5 МБ), открывается напрямую в браузере или с GitHub Pages.
- **Ванильный JS, без сборки, без фреймворков.** Код организован набором IIFE-модулей
  (`(function(w){ ... })(window)`), стили — в `<style>` внутри того же файла.
- Есть `data.json` (герои, мир и т.п.), но приложение самодостаточно в `index.html`.
- Хостинг планируется на **GitHub Pages** (статика).

## 2. Что уже готово (актуальное состояние)

Поток экранов: **Выбор героя → подтверждение → «путь» (интро) → тёмный игровой экран.**

- **Выбор героя** — оверлей `#zg-cs-overlay`. Герои берутся из глобального `characters`
  (фильтр `type === 'hero'`). Крупные портреты — из таблицы `HERO_ART_BAKED`
  (`images/heroart/*.png` + scale/x/y/fade). Есть «арт-тюнер» (скрытая шестерёнка 🖼).
- **Кнопка «Отправиться в путь»** — прозрачная, без рамки; пульсирует сама фраза (свечение
  текста), при наведении подсветка + «светлячки» снизу.
- **Поп-ап подтверждения** — `#zg-confirm-overlay`, драматичный (эмблема, разделитель,
  текст с именем героя, кнопки «Остаться» / «Да, в путь»).
- **Экран «пути»** — `#zg-journey-overlay`. Портрет = тот же, что при выборе, увеличен на 50%,
  затем растворяется. Фазы через классы `loading` (спиннер) и `dissolving` (портрет уходит).
  Тайминги в `zgJourneyStart`: `loading` @3.6с, `dissolving` @6.2с, переход @7.5с.
- **Тёмный игровой экран** — `#zg-game-overlay`. Пока **заглушка**: тёмный фон, шестерёнка ⚙
  в правом верхнем углу → панель настроек `#zg-game-settings` с единственной кнопкой
  «Покинуть игру». Текст-плейсхолдер «Инструментарий D&D · скоро». **Именно этот экран
  превращаем в VTT.**
- **Звук** — `window.ZargotaSound` (Web Audio). Есть звуки кубиков/бросков, и добавлен
  **атмосферный эмбиент волнами**: `ambientStart()` / `ambientStop()`. Волна: набег ~3.9с,
  затухание ~8.25с, пауза ~12с (период ~20.25с). Эмбиент играет на экранах выбора/пути/игры,
  уважает общий mute (`localStorage: zargota_sound_muted`).

Ключевые функции (все на `window`): `zgCharSelOpen/Close/Back/Editor/Choose/Pick`,
`zgJourneyConfirm/Cancel/Start/Close`, `zgGameOpen/Settings/Close`.

Z-index оверлеев: выбор 9500, путь 9600, игра 9650, подтверждение 9700.
localStorage: `zg_selected_char_id`, `zargota_sound_muted`.

## 3. Куда идём (цель)

VTT в стиле референса «Приключение в Мещере» (виртуальный стол, как Roll20/Foundry),
оформленный под тёмный мир игры. Компоненты будущего игрового экрана:

- Верхняя **панель партии** (портреты, имена, HP).
- Левый **лог/чат Гейм-мастера** (реплики персонажей + GM, поле ввода).
- Центр — **сцена/карта**: фон-карта, сетка, туман войны, токены героев (перетаскивание).
- Правый верх — **тулбар** (карта, журнал, музыка/mute, настройки, фуллскрин).
- Правая **линейка инструментов**.
- Правые панели: **инвентарь**, **быстрые действия**, **параметры** (сетка/освещение/
  затемнение/размер клетки), **меню GM** (журнал, сцена, настройки, покинуть игру).

## 4. Сетевая модель (согласовано с заказчиком)

**Формат игры:** 5 игроков + мастер. Модель **авторитарная, мастер-хаб**:
игрок отправляет **запрос** (напр. «переместиться на клетку X») → мастер **аппрувит** →
изменение применяется к общему состоянию → **все игроки это видят**.

**Важное ограничение:** GitHub Pages — только статика, **сам по себе он ничего не
синхронизирует** (нет сервера/БД/WebSocket). Живой обмен идёт через сторонний бесплатный
realtime-слой поверх статической страницы.

**Рекомендованный слой: Firebase Realtime Database.** Причины: бесплатный тариф с запасом
(100 одновременных подключений — нужно 6), работает из браузера по HTTPS (нет проблем с
NAT/TURN как в P2P), сам отдаёт актуальное состояние опоздавшим/переподключившимся, хранит
кампанию (persistence), даёт presence. Ключи в статике публичны — для Firebase это норма,
доступ закрывается правилами. Логин не нужен — работаем по **коду комнаты**.

**Рассмотренные альтернативы:** Supabase (Postgres + realtime, тоже ок, чуть больше настройки);
WebRTC/PeerJS (P2P, браузер мастера = хост; ниже задержка и без сторонней БД, но хрупче по
сети и без persistence). → *Здесь особенно интересно мнение Codex: возможно, ты предпочтёшь
Supabase, PartyKit, Ably/Liveblocks, или Yjs-CRDT — предлагай с обоснованием.*

### Предлагаемая структура данных (Firebase RTDB)

```
rooms/{code}/state          # авторитетное состояние (токены, HP, туман, лог). Пишет ТОЛЬКО мастер.
rooms/{code}/requests/{pid} # очередь запросов. Игрок пишет только в свою ячейку.
rooms/{code}/presence/{pid} # кто онлайн (onDisconnect).
```

Коды комнат короткие: 5–6 символов (напр. `K7F2Q`) — миллионы вариантов, этого достаточно.

### Правила безопасности (закрутить перед реальной игрой)

- `state` — запись только у мастера (идентификация мастера — см. открытые вопросы).
- `requests/{pid}` — игрок пишет только свою ветку.
- Старт в **test mode** (открыто), потом закрутить.

## 5. Инженерный подход (важно)

Два валидных пути, выбрать явно:

- **A. UI-first:** строим весь интерфейс на локальном объекте `gameState`, а Firebase
  подключаем в конце — просто заменяя «хранилище» состояния на синхронизируемое.
  Минимум переписывания, быстрый видимый результат.
- **B. Walking skeleton (заказчик склоняется сюда — «начнём с Firebase»):** сначала тонкий
  сквозной срез, чтобы доказать сеть раньше всего:
  1. Лобби на тёмном экране: «Создать комнату» / «Войти по коду».
  2. Подключение к Firebase + **presence** (кто онлайн).
  3. Один живой синхронизируемый объект — **общий лог/чат** (пишешь в одной вкладке,
     видно в другой).
  Дальше каждый элемент UI просто читает/пишет уже синхронизируемый `gameState`.

Рекомендация: даже при варианте B держать всё состояние в **едином объекте `gameState`**,
чтобы источник данных был один и легко подменялся.

## 6. Блокер для старта (нужно от заказчика)

Создать бесплатный Firebase-проект и передать `firebaseConfig`:

1. `console.firebase.google.com` → **Add project** (имя любое, Analytics можно выключить).
2. **Build → Realtime Database → Create database** → регион → **Start in test mode**.
3. **Project settings → General → Your apps → Web (`</>`)** → зарегистрировать → скопировать
   объект `firebaseConfig` (`apiKey`, `authDomain`, `databaseURL`, `projectId`, ...).
4. Передать `firebaseConfig` агенту.

Технические заметки:
- Firebase SDK подключать с CDN (модульный v9+ или compat). Приложение — один статический файл.
- Мультиустройственную синхронизацию тестировать на **URL GitHub Pages** (https), а не `file://`
  (у `file://` возможны заморочки с Firebase Auth — поэтому и берём модель без логина, по коду).

## 7. Открытые вопросы (решить с заказчиком / предложить)

1. Финальный realtime-слой: **Firebase** (рекомендация) / Supabase / P2P / иное?
2. Как отличать **мастера** от игрока: первый, кто создал комнату = мастер? Секрет мастера
   в URL? Отдельный «GM PIN»?
3. Идентификация игрока без логина: генерить `pid` и хранить в `localStorage`?
4. Разрешение конфликтов/очередь запросов: одна ячейка на игрока или список с таймстампами?
5. Карта: нужны **изображения карт/сцен** (в референсе — арт). Пока заглушка/сетка?
6. Персистентность кампании: храним весь `state` в RTDB (ок) — нужны ли «слоты сохранений»?

## 8. Стиль/ограничения кода

- Всё в `index.html`, ванильный JS, IIFE-модули, стили inline. Без сборщика.
- Аккуратные точечные правки большого файла; не ломать существующие модули.
- Держать новый игровой код изолированным модулем; состояние — в одном `gameState`.
- Русскоязычный UI. Тёмная золото-коричневая палитра (переменные `--gold`, `--gold2`,
  `--muted`, `--dim`, `--text`, `--border`).
